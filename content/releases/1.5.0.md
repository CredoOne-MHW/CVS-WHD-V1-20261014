## AS-IS

Everything from v1.0.0 to v1.4.0 is unchanged. The company workspace and its tabs, DPDP consent, the website builder, per-company cron and retention, the shared cache and every earlier fix behave exactly as they did.

## New Features

- **Each company gets its own Android app** (and iOS once signing is set up), built from one shared source in `mobile/`. A build carries that company's name, icon, colours, application id and its own address, so the app signs in to that company and nothing else.
- **Super Admin › Company › Mobile App** names and brands the app, takes a 1024×1024 icon, picks the platforms, and builds. Builds show Queued → Building → Ready with a link to the run on GitHub, the file size, who started it and how many times it was downloaded. A build can be cancelled or deleted, and **Your set-up now** lists every setting the build needs, green or red.
- **The build runs on GitHub Actions** (`.github/workflows/build-mobile.yml`) in this repository, next to the app source. The signed file is uploaded to that company's own S3 folder under `<COMPANY CODE>/app/<platform>/<version>/`, and the result is reported back signed with `MOBILE_BUILD_SECRET` — so only a build the platform started can report one.
- **No signing key is ever held by the platform.** Android and iOS certificates live in the build repository's GitHub secrets. The Android build stops rather than signing with a throw-away key, because a throw-away key means staff must uninstall the app — losing whatever is held on the device — to take the next version.
- **The company downloads its app** from Settings › Mobile App: the newest ready build per platform, with its version, size and date.
- **The app.** Sign in with the same e-mail and password as the web; the **DPDP notice** at the first sign-in and whenever a new version is published, which must be scrolled to the end before it can be accepted (recorded with source "app"); then a hamburger menu with **Dashboard**, **Chats** (arriving in v1.6.0) and **Profile**, which carries sign out and the version with its build number.
- **What the app shows follows the platform, not the build.** The Mobile Modules tab and each user's role are read when the app starts, so changing either needs no rebuild. Only the name, icon, colours, application id or address do.
- **Knowledge Base › GitHub build** explains the whole set-up: the repository, the platform settings, making the Android keystore, the repository secrets, the first build and what each failure message means.
- Builds that never report back are marked failed by the nightly housekeeping job after 90 minutes, so a row never spins for ever.

## Updates / Modifications

- `Company` gained `mobile`; `MobileBuild` is a new collection in the main database.
- `/auth/me` now returns `mobileScreens` for a company user — the Mobile Modules list the app reads at start-up.
- A company-side **Mobile App** module appears under Settings. Like every new module it starts switched off in each plan: tick it on the plans that should have it.
- New environment setting: `MOBILE_BUILD_SECRET`. The same value must be a secret in the build repository. The rest of the `GITHUB_BUILD_*` and `MOBILE_*` settings documented in v1.3.1 are now read.
