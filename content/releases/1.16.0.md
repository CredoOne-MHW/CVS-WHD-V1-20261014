## AS-IS

Everything from v1.0.0 to v1.15.0 is unchanged. **No screen, field, module or behaviour has been removed, renamed or moved.** Both additions below are new sections beside what was already there.

One promise is worth stating before anything else, because it is the thing most able to cause damage in this release:

> **Every QR code already printed on a leaflet still leads to exactly the form it led to yesterday.**

A form that has never been opened in the new editor keeps the same four fields, the same placeholders word for word, the same consent sentence, the same Submit button and the same thank-you page. Nothing is migrated and nothing is written until somebody presses Save. This is asserted value by value in the tests — including which two fields are required — rather than left to go well.

## New Features

### 1 · Mobile app branding — Super Admin → Company → Branding

You were right that there was nothing there. The app's sign-in screen could not be changed **at all**: it drew two letters in a circle, the company name, and one English sentence written into the app's source code. Changing any of it meant a new build and everybody reinstalling.

A new **Mobile app branding** section now carries:

| | |
|---|---|
| **App logo** | Shown in the circle. Falls back to the company logo, and to the two letters if you untick that. |
| **Sign-in banner** | The strip across the top — the banner that was missing. |
| **Heading** | Blank uses the app name. |
| **Line under the heading** | The sentence that used to be fixed. |
| **Footer note** | A small line above the version. |
| **Show the version** | On, as now. |

A preview of the phone screen sits beside the fields and updates as you type.

**These reach phones that already have the app.** The app asks for them on launch and remembers the answer, so a wording or logo change does not need a build. It also never waits: the screen draws from what it already has, then updates. With no network at all it shows what it was built with, so it is never blank and never half-drawn.

**The app icon and splash screen deliberately stay on the Mobile App tab.** Those are part of the installed package and only a build can change them — putting them here would suggest otherwise, and the section says so.

### 2 · Design your own campaign form — Company → Integration → **Form**

The QR / campaign form had four fixed fields written into the page. The connector now has a **Form** tab:

- **Add questions** — single line, paragraph, e-mail, phone, number, date, dropdown, choice, tick box — with options, placeholders and required.
- **Reorder** anything, including the built-in fields.
- **Reword** every label, the button, the consent line and the thank-you page.
- **Switch off** e-mail or the message if you do not want to ask.
- **Preview** the real page before saving.

**Answers to questions you add arrive on the lead as custom fields**, under the label you gave them. This is the part that needed the most care: the lead mapping keeps only the keys it recognises and silently drops the rest — so without new code a company could add a question, a visitor could answer it, and the answer would be thrown away with nothing logged anywhere. Only keys the saved form actually declares are carried across, so the public endpoint cannot be used to push arbitrary data onto a lead.

The form's own rules are enforced **on the server too**, not only in the browser. The page posts to a public endpoint and anything can call it directly, so the browser's checks are a courtesy to the visitor and nothing more.

## Update / Modifications

### Two limits on the built-in fields, and why

**Name and mobile number cannot be removed, renamed, switched off or made optional.** A lead is a person and a way to reach them; without both there is nothing anybody can act on, and the rest of the pipeline — deduplication, WhatsApp, assignment — is built on them.

**The four built-in fields keep their keys and their types.** The key is what puts an answer into the lead's own name, phone, e-mail and comments columns. If renaming a label also renamed the key, the form would go on looking correct while the lead's phone column quietly stopped filling. Labels are yours to change; keys are not, and the editor shows each one so it is never a mystery.

If you want name or phone to be optional, say so and I will do it — but I would want to say first what it does to deduplication.

### One list of brand images instead of three

While adding the two app images I found the upload route, the delete route and the public read route each kept their own copy of the list of allowed image kinds. Three lists is how an image uploads successfully and then returns "not found" when it is read back. There is one list now and all three read it. No existing image is affected.

## Still waiting on you from v1.15.0

For a company built in any colour but the default, each is green next to its own branding. **Say "Allow" and it goes into the next release.** Colour only; no layout, behaviour or permission changes. Untouched in this release.

## Performance

Nothing new on any page load.

The form page already fetched its details before drawing; the fields now come back in that same response, so it is the same single request it has always made. The app's branding is one small request on launch that nothing waits for, answered from a cache on every launch after the first, and cached for five minutes at the edge besides. No new database collections, no new indexes, no schema changes — the form lives in the connector's existing settings field and the branding in the company's existing branding field.

## Logs

Unchanged, and both additions are covered by what already exists. Saving a form is a connector update and is recorded as one; saving branding is a company update and is recorded as one. A submission that the server turns away is recorded by the request log like any other refusal.

## Verified

- `npm run preflight` — all five stages; **280 checks**, including **55 new ones**.
- The regression checklist gains a new section with entries **38** to **43**, all guarded by `test:forms`.

Most of those 55 are the compatibility promise at the top of this note, checked one value at a time. Two are worth calling out because they guard mistakes rather than symptoms:

1. **The original wording is pinned literally in the test**, not compared against the defaults in the code. Comparing the code to itself passes happily when somebody rewords a default — I confirmed that by rewording one and watching the wrong check stay green.
2. **The app cannot import `shared/`** (that is checklist row 14), so the sign-in sentence necessarily exists twice. The two copies are asserted to match word for word, because two copies of a string are two strings that drift — and the symptom would be a screen that says one thing before it reaches the network and another after.

Each new check was confirmed to fail when the thing it guards is broken.

**What cannot be verified here:** no phone and no live company in this container. The preview image is a redraw from the components, not a screenshot.
