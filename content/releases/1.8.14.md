## AS-IS

Everything from v1.0.0 to v1.8.13 is unchanged. No screen, field or behaviour was removed.

## On the build log

The 123 lines from that run are **41 warnings and no errors**. They are Hermes compiler notes about JavaScript globals — `setTimeout`, `fetch`, `document`, `WebSocket`, `jest` — used without declaration, every one of them from inside a library: React Native's own polyfills, React's scheduler, `react-native-reanimated`, `get-intrinsic`, `pusher-js`. None come from this project's code, none can be fixed from here, and every React Native app produces them. The file they are reported against, `index.android.bundle`, only exists because bundling **succeeded**.

Two real bugs were found while checking, both mine, and both fixed below.

## Fixes

- **The mobile app was never actually typechecked.** `npx tsc --noEmit` in `mobile/` has been run before, but always without `node_modules` installed, so it failed on unresolved imports and never reached the code. Run properly for the first time, it found a genuine error: `src/lib/live.ts` loads pusher-js with a dynamic `import()`, and Expo's base config sets `target` but not `module`, leaving it at a level that predates dynamic import. **`module: ESNext` is now set**, and the app typechecks clean.

  A check that cannot run is worse than no check, because it reports success.

- **A screen whose data never arrived said nothing at all.** There are 63 places that load a screen with `api(...).then(setState)` and no `.catch`. If the call fails, the state is never set and the screen sits on a spinner with nothing to explain it — the same bug fixed on the Mobile App tab in v1.7.0, present on many other screens.

  The global handler that exists for exactly this **was skipping them on purpose**, with the comment *"API errors are already shown to the user as toasts"*. That is true of a call with a `.catch` — and those never reach a global handler. The ones that do are precisely the calls with no `.catch`, so the premise was backwards and the one thing that could have surfaced these was configured not to.

  An unhandled API failure now raises a toast saying what happened: *"You do not have permission for that."*, *"That was not found."*, or the platform's own message with *"Please try again."* One change, covering all 63 and anything added later.

## Verified

- **The mobile app bundles**: 1,219 modules, no errors, after the tsconfig change.
- **Both typechecks clean** — platform and app.
- **The silent failure is gone**, tested in a browser with every API call failing: Role Management now shows *"Database unreachable. Please try again."* where it used to spin with nothing on screen.
- `npm test` — 53 checks, all passing.
