## AS-IS

Everything from v1.0.0 to v1.8.6 is unchanged. No screen, field or behaviour was removed.

## Fixes

- **Uploading a branding image showed an error that explained nothing.** The error handler turned **any** error that was not one of ours into *"Internal server error (ref …)"*. Two ordinary, fixable things landed there:

  1. **An image over the size limit.** The limit was **3 MB**, which an ordinary side banner exceeds without trying. The upload was refused by `multer` before it reached any of our code, so nobody was told the size was the problem.
  2. **Any refusal from S3** — wrong bucket name, missing permission, an expired key — came back the same way, with the actual reason only in a server log.

- **Both now say what to do**, translated once in the error handler so every upload in the platform benefits — branding, knowledge base, DPDP documents, notification sounds, client attachments:

  | What happened | What you now see |
  | --- | --- |
  | Image too big | *"That file is too large. The most this accepts is 8 MB — save it smaller and try again."* |
  | Bucket wrong | *"File storage: The S3 bucket named in S3_BUCKET does not exist. Check the name and the region."* |
  | No permission | *"File storage: S3 refused the write. The access key needs s3:PutObject on this bucket and prefix."* |
  | Key wrong | *"File storage: S3 does not recognise AWS_ACCESS_KEY_ID."* |
  | Secret wrong | *"File storage: S3 rejected the signature — AWS_SECRET_ACCESS_KEY does not match the key id."* |

  A genuine fault is still a 500 with a reference number and still keeps its message off the screen. That has not changed.

- **The branding image limit is now 8 MB**, up from 3 MB. The company-logo upload on the company form was 2 MB and now matches.

- **The browser refuses an impossible image immediately.** Picking one that is too large, or not an image type the platform accepts, says so the moment it is chosen — rather than after it has been uploaded and rejected.

- **An image that fails now says which one.** Three images are uploaded in a row after the company's details are saved; a failure used to give one message with no indication of which. It now names the image — and makes clear the details themselves were saved, because they were.

## Verified

Twelve cases, no database needed: `npm test`.

- every `multer` limit and every S3 refusal maps to its own sentence, with the right status;
- our own errors, duplicate keys and genuine crashes all behave exactly as before;
- a genuine crash still does not leak its message to the browser.
