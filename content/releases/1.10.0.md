## AS-IS

Everything from v1.0.0 to v1.9.0 is unchanged. **No screen, field, module or behaviour has been removed, renamed or moved.** Every existing user, role, permission, conversation, build, connector and setting works exactly as it did before this release.

Specifically preserved:

- **Every URL already printed, pasted or in a QR code keeps working.** The addresses shown for connectors now read as the company's own domain, but the old deployment address still answers — both reach the same application. Nothing in the field breaks.
- **The Staff / Customer switch stays.** You asked to remove it from the app; because removing it was the only way to create a Customer from a phone, it has been made compact instead, exactly as you chose. The web is untouched.
- **The Android build pipeline is unchanged for direct-install builds.** The same signing key, the same callback, the same S3 upload.
- **Cancelling a build still works** and still answers on the old address; "Stop" is the same action under a clearer name.
- **No screen moved in the interface pass.** Spacing, type size and corner radii changed; layout did not.

## New Features

### Watch a build, and pause or stop it

Super Admin → Company → **Mobile App** and → **Mobile App Release** now show any running build above the table, with a live bar, a percentage and the step it is on — *Waiting for a build machine*, *Installing the app's packages*, *Making the native project*, *Compiling and bundling*, *Uploading the finished app*. The figures are reported by the build itself as it passes each step, so they are a record of what happened rather than a timer pretending to be progress. The page now refreshes every 5 seconds while something is running, instead of every 20.

Three controls appear while a build is live, in both places: **Pause**, **Resume** and **Stop**. Stop asks to confirm first.

> **Please read this one.** GitHub Actions has no pause. A run is either going or cancelled; nothing can freeze a build machine mid-step and pick it up later. So **Pause cancels the run and remembers the version and build number, and Resume starts that same version again from the beginning.** The screen says exactly that under the bar — *"Resume starts it again (same version)"* — so nobody expects it to carry on from 60%. This is the same behaviour, and the same wording, as the FnB installer screens you sent. If you would rather Pause simply did not exist, say so and it comes out.
>
> Resume reuses the same row rather than creating a new one, so the history does not fill with half-builds, and a tester who was told to expect v1.0.0.17 still gets v1.0.0.17.

### App store credentials, and why the iOS button is grey

Mobile App Release has a new **App store credentials** panel, under *Start a build*. It lists three groups — **iOS signing**, **App Store Connect** and **Google Play** — and for each one: what it unlocks, where it comes from, which parts are already saved and which are missing. Files are uploaded directly; everything is sealed to the build repository's public key and stored as a repository secret. **Nothing is kept in this platform's database**, and GitHub never gives a secret's value back, so the panel can show that something is present but never what it is.

**The iOS button is no longer a dead grey button.** It now says why, on hover and in a banner: *"4 of 4 Apple credentials are missing. They cannot be generated here — they come from an Apple Developer Program membership."* Add them and **iOS switches itself on**, with nothing further to set.

This matters because of a trap that was already there: iOS previously needed `MOBILE_IOS_SIGNING=1` set by hand on the platform **as well as** the certificates in the repository. Somebody could have supplied every certificate correctly and still found the button grey, with nothing on screen explaining it. Having the credentials is now the condition.

**What is still needed from you, and cannot come from here:** an Apple Developer Program membership (99 USD/year), a distribution certificate (.p12 and its password), a provisioning profile, and an App Store Connect API key (.p8, Key ID, Issuer ID). The whole iOS pipeline — macOS runner, `pod install`, `xcodebuild` archive, export and upload to App Store Connect — is already written and waiting.

### Store compliance

- **iOS builds now run on `macos-15`.** This is a real defect found while checking: the workflow used `macos-14`, which carries Xcode 15, and **App Store Connect refuses a build made with an Xcode that old** — it would have failed at upload, after a twenty-minute build.
- **The Android API level is now set explicitly to 35** rather than left at Expo's default of 34, which Google Play no longer accepts for updates. It is a setting (`ANDROID_TARGET_SDK`), not a hard-coded number, because Play raises this bar every August and the day it moves is the day an upload starts being refused — raising it should not need a code change and a release.
- **The export-compliance answer is declared** (`ITSAppUsesNonExemptEncryption: false`), which is correct for an app that only speaks HTTPS and stops every App Store upload stalling on the same emailed question.

### Group chat from the phone

The app's Chats screen now has **New group** beside **New chat**: a name, a search, and tap the people to add. It appears only for someone whose role allows it — the same permission the web checks — so a tele-caller does not get a button that answers "not allowed". Names and roles only, as everywhere in chat.

### The app tells you when there is a newer version

A bar appears across the top of the app when a newer build exists: *"Version 1.0.0.17 is available — tap Update to download and install it."* It is checked when the app opens and each time it returns to the foreground. **A push notification also goes out the moment a build finishes**, to that company's phones that are not already on that version.

An Android app installed from an `.apk` has no store to update it, so without this a phone can sit on an old build indefinitely with nobody aware. Only installable builds are announced — a store build is an `.aab` or an App Store `.ipa`, which no phone installs directly. A version somebody dismisses stays dismissed until a newer one exists.

## Update / Modifications

### Fixed: QR code and campaign form URLs showed the platform's address

Under **Integration**, the endpoint URL and the hosted form URL were built from `APP_BASE_URL` — the Vercel deployment address — rather than the company's own. A QR code printed for a camp, or a form URL pasted into a campaign, is seen by the public and lives for months on a poster; it has to read as the company's own address.

They now use the company's **custom domain** if it has one, otherwise its **subdomain of the platform's base domain** (`credoone.mhw.credovation.tech`), falling back to the old behaviour only if neither is set. **Both addresses reach the same application, so this changes what is shown and copied, never where it goes — every URL already in the field keeps working.** The lookup is cached for a minute per company, so listing twenty connectors does not re-read the same two fields twenty times.

### Chat attachments can be downloaded

Every attachment now has a **download** control — a button on a file, and one that appears over an image on hover (a **Save** link on the phone). It fetches a separate link that saves the file **under its own name** rather than the random key it is stored as. The link for *viewing* deliberately does not carry that, so a picture can still be shown in place.

### The attachment limit is 20 MB, and says so in your words

Raised from 15 MB. A file over the limit is refused **before it is uploaded**, in the browser and on the phone, with the exact wording you asked for: **"Exceeded File Size"**, followed by the actual size and the limit. The server says the same if something reaches it. There is now a test asserting that exact phrase, so it cannot drift.

### A more compact interface

As agreed — **density and polish, with no layout changes**. Table rows, inputs and buttons each lose a few pixels of padding, the type scale is slightly tighter, corner radii are consistent, and focus rings are less heavy. On a table of twenty rows this is most of a screenful recovered. Every section is exactly where it was.

On the phone: one shared scale of four spacing steps, three radii and five type sizes, replacing a mix that made screens read as assembled rather than designed. Dashboard tiles now lead with the number rather than an upper-case caption; conversation rows and chat bubbles are tighter; the Staff/Customer switch is a compact inline control instead of a full-height section, which had been pushing **Save** off the bottom of a small screen.

### Also

- **Users** was added to the app's screen list in v1.9.0; it still has to be ticked under Super Admin → Company → Mobile App for a company whose screen list was already saved.
- A build that is paused is no longer flipped to "cancelled" by the run it just cancelled, which used to arrive a second later and take the Resume button away from a row somebody was still looking at.

## Performance

- The connector address is cached a minute per company — one read instead of one per connector per page.
- A running build is polled every 5 seconds and a paused one not at all; nothing changes about a paused build until somebody presses Resume.
- Progress is pushed by the build rather than polled from GitHub, so following a build costs no GitHub API calls at all.
- The app's update check is one small public request on launch and on returning to the foreground, and is skipped entirely when the platform does not answer.
- Attachment bytes never pass through the database; the upload streams to S3 and the message carries only a key.

## Logs

- Pause, Resume and Stop are each recorded with who did it, which company and which version.
- Opening and downloading an attachment are recorded separately, with the file's name.
- Saving store credentials is recorded by which credential names were written — never their values.

## Verified

- `npx tsc --noEmit` clean on both the platform and the app.
- `npm test` — **93 checks**, including 24 new ones covering the progress contract, the pause guard, version comparison and the store-compliance settings.
- `npm run build` clean.
- `npm run verify:bundle` — Metro bundles the app exactly as Gradle does, confirming `expo-build-properties` resolves.

**What could not be verified here:** this container has no Android SDK and no macOS, so the **Gradle** side of the API-35 change and the **Xcode** side of the `macos-15` change are untested until the first build after this release. The API level is one setting if it needs to go back to 34. Everything else is covered above.

**A known gap, stated rather than hidden:** Google Play also expects 16 KB memory-page support for apps targeting recent Android versions. That needs a newer Expo SDK than the one this app is on (51), which is its own piece of work and not something to fold into this release.

## Build repository

`mobile/` and `.github/` must be pushed to the build repository with this release. **This release changes the workflow and adds a native dependency** (`expo-build-properties`), so a stale copy would fail. The revision markers were bumped to `1.10.0` for exactly that reason — Mobile App Release will report the repository as behind until it is pushed.
