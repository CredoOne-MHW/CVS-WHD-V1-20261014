## AS-IS

Everything from v1.0.0 to v1.6.0 is unchanged. Leads, clients and the service board, client deletion by OTP with its archive, the Super Admin company workspace and every one of its tabs, DPDP consent, the website builder, the per-company apps and their GitHub build, chat with its groups and notices, push notifications, per-company cron, retention, the shared cache and every earlier fix all behave exactly as they did. Nothing was removed.

Two things on that page were changed, both with your approval, and both are set out under *Updates / Modifications* below.

## New Features

- **The Mobile App tab no longer hangs.** It had no error handling at all: a single failed call left it spinning for ever with nothing on screen and no way to find out why. It now says what went wrong — including the status and the platform's own message — and offers **Try again**. The rest of the company page was never affected and still isn't.
- **Super Admin → Mobile App Release** is a new module. Every company's app in one place:
  - **Four counts across the top** — building now, ready and failed over the last seven days, and how many phones are on the newest version of *their own company's* app (each company has its own version line, so this is worked out per company and then added up).
  - **Start a build** for one company, or for **every company that already has an app**. A company with no app yet is deliberately skipped by the bulk action — its first build fixes the application id and the signing key, which is not something a bulk action should decide.
  - **Every build, across every company**, with filters for company, platform and status, what started it (by hand, on a push, or across every company), and a link to the run on GitHub. A running build refreshes itself until it finishes.
- **Automatic rebuilds on new code.** A push to the app's own repository rebuilds the app of every company that has *Auto build* on, each with its own name, icon, colours and address; phones get it as an ordinary update. There are two ways to connect it and both are in the panel: a step in the repository's workflow, or a repository webhook (`/api/public/webhooks/github/push`, content type JSON, "Just the push event"). Both are signed with **BUILD_TRIGGER_SECRET**, which the screen shows, copies and can replace. A push to any branch other than the one being watched is accepted and ignored, so a feature branch never rebuilds anyone's app.
- **The Build screen on each company** now shows, before the list of builds:
  - **Downloads** — one card per platform with the version that is actually live, its size, when it finished, its full S3 path and a download button.
  - **Android signing** — the key this company's app is signed with, in plain words, with the application id, the alias, the version it has applied from and the certificate fingerprint.
- **A signing key that lasts, kept by the platform.** The platform now makes **one permanent Android key per company** at that company's first Android build and signs every later build with it, so an update installs over the old app instead of being refused.

## Updates / Modifications

- **Signing keys — this reverses a decision made in v1.5.0, with your approval.** Until now keys lived only in the build repository's GitHub secrets and the platform never held one. The platform now makes and keeps a key per company. How it is protected:
  - the keystore and both passwords are **encrypted with AES-256-GCM** before they are written, under a new setting `MOBILE_SIGNING_SECRET`. The database on its own cannot sign anything.
  - the key is **never a workflow input**, because inputs are printed in the run's own log. The build asks for it over the same signed channel it reports its result on, only while it is still running, and shreds the file when it finishes.
  - nothing in the key ever reaches a browser. The screens only ever see the fingerprint.
  - **a repository that already has `ANDROID_*` secrets still works**: if the platform has no key for a company, the build falls back to the repository's own, exactly as before.
  - **one reinstall, once.** A phone holding an app built before the platform's key needs a single uninstall-and-reinstall; every update after that installs over it. The Build screen says so, per company, and only while it is actually true.
- **The Build section of Super Admin → Company → Mobile App was restructured**, as approved: Downloads, then Android signing, then the builds list. **The builds table itself is unchanged** and still sits underneath with its download, cancel and delete actions.
- **`MobileBuild` gained three fields** — `signedBy`, `signingFingerprint` and `trigger` — and an index on `status`+`createdAt` for the all-company list. Existing rows are untouched; an older build simply has no value in them.
- **New module `mobile_release`.** Like every new module it starts **switched off**: give *Mobile App Release* to the Super Admin roles that should have it, under Role Management.
- **New settings:**
  - `MOBILE_SIGNING_SECRET` — required before the platform can keep signing keys. Without it, nothing breaks: builds fall back to the repository's `ANDROID_*` secrets and the Build screen says so.
  - `APP_BASE_URL` is now also used for `PLATFORM_URL` on the set-up panel. It was already in use elsewhere.
  - The build workflow gained one input, `signing_url`, and one secret it already had, `MOBILE_BUILD_SECRET`, is now also used to collect the key.
- **The `.github/workflows/build-mobile.yml` signing step was rewritten.** It used to fail outright when `ANDROID_KEYSTORE_BASE64` was missing. It now takes the platform's key first, the repository's secrets second, and only fails when there is neither — with a message saying which of the two to set.
- One wording fix on the Build screen: "A Android build is running now" now reads "An Android build is running now."
