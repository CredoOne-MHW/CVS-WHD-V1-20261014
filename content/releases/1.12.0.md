## AS-IS

Everything from v1.0.0 to v1.11.2 is unchanged. **No screen, field, module or behaviour has been removed, renamed or moved.** Every existing lead, client, payment, ticket, conversation, webhook, user and build works exactly as before.

Specifically preserved:

- **Every webhook keeps every setting.** The page is now a list; editing opens the same card with the same fields, the same preview and the same **Send test** button. Nothing was dropped on the way.
- **"No of Licenses" is a label change only.** The stored field is still `licenses` in the database and in the API — renaming it would mean migrating every lead, client and payment row for a word on a screen, and would break anything already reading it.
- **The Journey shows the same events in the same order.** Only its layout changed.
- **Chats, attachments, groups and notices** on the phone are untouched apart from spacing.
- **Staff dashboards keep every figure they had** — the four tiles are still the first thing on the screen.

## New Features

### Support tickets on the phone

A new **Support tickets** screen, for both kinds of user, with filter chips across the top (All / Open / In Progress / Resolved / Closed, each with its count) and a full history on each ticket showing every status change, who made it and any note.

**Customers can raise a ticket.** A floating button on both the home screen and the ticket list opens a short form — what it is about, and what happened. They get the WhatsApp updates they already would have.

> **How a customer is kept to their own tickets.** The customer screens read `/co/my-tickets`, which scopes every query to **the client record on the sign-in** — never to a permission. A permission answers "may this kind of person read tickets", which is the wrong question: it would let one customer read another's support history. This is important enough that there is now a test which reads the route code and fails if anyone later adds a permission check to those endpoints, accepts a client id from the request, or forgets the company scope.

This screen appears in Super Admin → Company → Mobile App as a new tick box, **Support tickets**. For a company whose screen list was already saved it must be ticked before it appears.

### The home screen, rebuilt for each kind of user

**For staff and administrators** — the four tiles are still first, then:

- **Lead status** — open leads as a labelled bar for each stage, drawn against the largest so a small stage is still visible rather than a one-pixel sliver.
- **Support tickets** — open against resolved as one split bar, plus tickets waiting over 48 hours, grievances, and the average time to resolve.
- **Response** — leads not contacted in 24 hours, and how long the oldest new lead has been waiting.
- **Chats** — unread messages and how many conversations they are spread across, and how many groups you are in. Counted **from your own membership**, because "12 unread" is only useful if the twelve are addressed to you.
- A red strip when follow-ups are overdue.

**For customers** — their name and client code, what is with you now, what has been resolved, and their tickets as a four-part bar. Nothing about the business, because none of it is theirs.

All of it arrives in **one request**. A phone on a patchy connection should not make five calls to fill one screen — it is either there or not, never four spinners. The figures come from the same insights the web dashboard uses, so the phone and the desk can never disagree about how many leads there are.

Charts are drawn with plain views rather than a charting library: a handful of bars and a split bar do not justify a megabyte of bundle and another native dependency.

## Update / Modifications

### "No of Licenses" is now "Qty"

Everywhere it appears: the service/product rows on a Lead and a Client, the Payment Details table header, the read-only field on a payment row, the help text, the CSV import columns, and the screen-reader labels. **Label only** — see AS-IS above for why the stored field keeps its name.

### Fixed: the Journey panel

It had `max-h-[42vh] overflow-y-auto` of its own, **inside a drawer that already scrolls**. That produced two scrollbars side by side and entries that looked cut off halfway down a panel with plenty of room beneath them — and the inner one swallowed the wheel whenever the pointer happened to be over it. Nobody can scroll two things at once.

It no longer scrolls: it is as tall as its contents and the drawer scrolls, once. The rail and markers are now laid out from the list itself instead of being pulled into the margin with a negative offset, which is what made them drift out of line as text wrapped.

### Webhook templates are a list

Every webhook used to be drawn fully open — URL, template, separator, limits, preview, all of it — so eight webhooks made a page metres long with no way to see what you had.

Now each is **one row**: name, on/off, and the endpoint. Click it to see a plain summary (endpoint, template, how the message is joined, where it splits, who else gets a copy, and the schedule if it has one). **Edit** opens the full card in a modal; **delete** is an icon on the row with a confirmation. A list answers "what do I have, and is it on?" in one screen, which is what this page is used for far more often than editing.

### Fixed: the polling note was hidden behind the buttons

On the app's Chats screen, *"Messages refresh every few seconds"* was the last element in the view, which put it **underneath** the floating **New chat** and **New group** buttons — half of it unreadable. It is now a quiet strip at the top, where nothing overlaps it.

### A more compact chat list

Tighter rows, a smaller search field and smaller buttons — about two more conversations visible on a phone screen, with the avatars slightly larger so the list is still easy to scan.

## The regression checklist you asked for

You asked that fixed bugs should not come back, and that there be a checklist checked before every release. That is now a file and a command rather than a promise.

**`REGRESSIONS.md`** lists all **30** failures this project has had, what each one was, which release it cost, and the named check that now stops it.

**`npm run preflight`** runs typecheck (platform *and* app), the full test suite, the production build and the Metro bundle — then prints that checklist with a result against each line, and lists the nine that still have no automated guard so they are confirmed by hand rather than forgotten. It stops at the first failure, because a release is not partly ready.

The checklist is parsed out of `REGRESSIONS.md` itself rather than duplicated in the script, so the document people read and the thing that runs cannot drift apart. **It proved itself immediately:** the first run of this release failed because the release note was missing.

## Performance

- Each home screen is **one request**, assembled in parallel on the server.
- Chat figures come from the conversations you are a member of, not from a scan of the company's.
- Ticket filtering and chat search happen on what is already loaded — no request per keystroke.
- The webhook list renders rows rather than a preview engine per webhook, so the page no longer re-computes every template on every change.

## Logs

- Raising a ticket from the phone is recorded as *"Raise support ticket"* with its number, exactly as the web does.
- Every status change still records who made it, when, the note, and whether the WhatsApp message went out.

## Verified

- `npm run preflight` — all five stages pass; **168 checks**, including **21 new ones** asserting that a customer cannot reach another customer's records.
- The checklist prints 21 automated lines covered and 9 to confirm by hand.

**What could not be verified here:** no Android or iOS emulator, so the app previews sent with this release are hand-built layout previews, not device screenshots. The real rendering comes from the build.
