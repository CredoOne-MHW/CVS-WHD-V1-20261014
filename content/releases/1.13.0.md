## AS-IS

Everything from v1.0.0 to v1.12.0 is unchanged. **No screen, field, module or behaviour has been removed, renamed or moved.**

Worth stating plainly before anything else: **the platform has been sending a notification for every new message since v1.6.0.** The server side was already complete — the right people, the sender's name, the thread it belongs to, group messages prefixed with who spoke. This release is about the three things between that and a banner appearing on a phone.

## New Features

### Tapping a notification opens what it is about

Previously a tap opened the app wherever it was last left, which makes a notification almost pointless — you are told there is a message and then have to go and find it.

A tap now opens that conversation. This works in both cases, which are not the same thing: the app already running, and the app **started by the tap** — the second needs the stored response, because the listener is attached after the response has already gone.

### A message for the conversation you are reading does not interrupt you

If a message arrives for the thread already on screen, there is no banner and no sound. It is already visible; a notification for something you are looking at is noise. Every other message alerts as usual.

### The number on the app icon

The badge follows the real unread total across every conversation, and clears when there is nothing waiting.

## Update / Modifications

### Fixed: customers — and several staff roles — could never receive a notification at all

A real bug, and the reason "push notifications for all users" was not already true.

Registering a phone for notifications went through an endpoint gated on **Chats read** permission. Anybody without that module — **every customer**, and any staff role that does not include chat — was refused, so their phone was never recorded, so nothing could ever be sent to it. Not a message, not a notice, not a ticket update.

Registering a device is about *this phone belonging to this person*; it is not a chat action. It now needs only a valid session. **What may be sent to somebody is still decided when each notification goes out**, exactly as before — this changes who can be reached, not who is told what.

### Super Admin now shows whether notifications can reach anyone

Under **Company → Mobile App**, a Notifications panel: how many phones are registered and how many are reachable, broken down by platform. A phone appears there only once it has obtained a push token and sent it in — so **"no phone has registered yet"** is the clearest sign that the credentials below are missing, rather than that nobody has installed the app.

## What is still needed from you, and cannot come from here

Stated plainly, as with iOS signing. **Two credentials, and without either one no notification will arrive on an installed app — however correct everything else is.**

**1 · Expo project ID** — from expo.dev. An installed app cannot obtain a push token without it; only an app running inside Expo Go can. No token means the phone is never registered, which is what the panel above will show.

**2 · Firebase config (`google-services.json`)** — from the Firebase Console, for an Android app whose package name matches the company's application id exactly. Expo delivers Android notifications **through Firebase**: without this, messages are accepted by Expo and then silently dropped. There is nothing in any log to see, which is precisely why this is worth reading twice.

Both are now in **Mobile App Release → App store credentials → Push notifications**, alongside the Apple and Google Play ones, with instructions for where each comes from. Add them and the **next build** will carry them.

A build missing either one **still succeeds** — the app simply has no notifications — but it now prints a loud warning naming which is missing and where to put it, instead of producing an app that quietly receives nothing.

## Performance

No new requests. Notifications travel over the service that was already in use; the badge is computed from the conversation list already loaded.

## Logs

Unchanged. Registering and forgetting a device are recorded as before.

## Verified

- `npm run preflight` — all five stages; **191 checks**, including **23 new ones** covering every link in the chain from a message being sent to a banner appearing.
- The regression checklist gains two entries (**31** and **32**), both guarded by `test:push`.

**What cannot be verified here:** no phone and no Firebase project in this container, so end-to-end delivery is not something I can prove. What is proved is that every link this project controls is in place and that the two it does not control are asked for, carried into the build, and warned about when absent. **The first real test is a build with those two credentials in place, installed on a phone.**
