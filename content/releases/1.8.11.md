## AS-IS

Everything from v1.0.0 to v1.8.10 is unchanged. No screen, field or behaviour was removed.

## The problem this solves

Every release has **two halves that deploy separately**:

| Half | Where it goes | How |
| --- | --- | --- |
| The platform | Vercel | Deploy |
| `.github/` and `mobile/` | Your build repository | **Commit and push** |

Deploying the platform does **not** change the workflow GitHub runs. So a build can keep failing on something that was fixed two releases ago, with nothing on screen to suggest why — the panel is reading the platform's own settings, while GitHub is running a file from last week.

## Fixes

- **The workflow now carries a revision**, `# lms-workflow:`, and the platform knows which one it expects. **Check GitHub setup** reads the file in your repository and compares, so *Workflow file* now says one of:

  - *"…is on main, revision 1.8.11 — current."*
  - *"…on main is revision 1.8.0; this platform ships 1.8.11. Push the .github folder from the current release."*
  - *"…is on main, but it is an older copy from before the revisions were marked."*

  The revision only changes when the workflow or one of its scripts actually changes, so it does not cry wolf on every release.

- **A test keeps the two honest.** `npm test` fails if the marker in the workflow and the constant in the platform ever disagree — a check that lies is worse than no check.

## If you are seeing `python3: can't open file …android-signing-config.py`

That message can only come from the **old** workflow. The word `python3` does not appear anywhere in v1.8.10 or later. Push `.github/` to your build repository and the error goes with it.

Delete the two `.py` files while you are there — they were replaced by `.mjs` in v1.8.10 and will otherwise sit in the repository doing nothing.
