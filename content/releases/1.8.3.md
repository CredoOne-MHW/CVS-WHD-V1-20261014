## AS-IS

Everything from v1.0.0 to v1.8.2 is unchanged. No screen, field or behaviour was removed.

## Fixes

- **"Internal server error (ref …)" when starting a build from Mobile App Release.** `startBuild()` explains itself — *"GitHub refused the build (404)…"*, *"Switch on S3 storage for this company…"*, *"An Android build is already running…"* — and the release console let every one of those escape as an unhandled exception, which the error handler turned into an opaque reference number. The company's own Mobile App tab had caught them correctly since v1.5.0; this route never did. **The real reason is now shown.**

  In the case reported, the message underneath was almost certainly *"GitHub refused the build (404). Push .github/workflows/build-mobile.yml to the branch and open the Actions tab once so Actions are enabled."* — because `GITHUB_BUILD_WORKFLOW` is still set to `build-desktop.yml`, which belongs to another project and does not exist in this repository.

## New Features

- **"Check GitHub setup" now actually asks GitHub.** It used to re-read this platform's own settings, which can only ever tell you a value is present and well-formed — never whether it is *true*. It now asks four questions and gives four plain answers, each with what to do:

  | | |
  | --- | --- |
  | **Repository** | Can the token see `owner/repo` at all? Separates "does not exist", "no access" and "token expired". |
  | **Branch** | Does the branch being built from exist? Names the default if not. |
  | **Workflow file** | Is `.github/workflows/<name>` actually **on that branch**? This is the one that bites. |
  | **Actions** | Has GitHub registered the workflow? It does not until Actions has been opened once. |

  Every answer that is wrong carries the fix, not just the complaint.

- **A workflow name from another project is now flagged.** The platform ships exactly one workflow, `build-mobile.yml`, so anything else gets an amber note — and where the name contains "desktop" it says plainly that it is another project's and will not build an app. **It does not block the build**, because renaming a file on purpose is legitimate; *Check GitHub setup* is what settles it.

- **`BuildRequirement.warn`** is new, beside `check`: a value that is not broken but is probably not what was meant. A `check` blocks, a `warn` does not. Existing requirements are unaffected.

## What to do with this release

1. Set **`GITHUB_BUILD_WORKFLOW=build-mobile.yml`**, or remove the variable entirely — that is already the default.
2. Make sure `.github/workflows/build-mobile.yml` is **committed and pushed** to the branch you build from. It is in the release zip, inside the hidden `.github` folder (`Cmd ⇧ .` on macOS, View → Hidden items on Windows).
3. Open the repository's **Actions** tab once. GitHub does not register a workflow until somebody has.
4. Press **Check GitHub setup**. It will tell you which of those four is still wrong, if any.
