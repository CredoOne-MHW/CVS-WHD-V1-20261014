## AS-IS

Everything from v1.0.0 to v1.8.3 is unchanged. No screen, field or behaviour was removed.

## Fixes

- **`GITHUB_BUILD_WORKFLOW` is no longer read.** It was a setting with exactly one correct value and one very easy wrong one.

  The sibling restaurant platform has a variable of the same name naming a **desktop installer** workflow. Environment files get copied between projects, so `build-desktop.yml` arrived here and pointed a mobile platform at a workflow that does not exist in this repository. Every build answered **404**, and because of the bug fixed in v1.8.3, that 404 arrived as *"Internal server error (ref …)"*.

  This platform ships exactly one workflow and builds mobile apps. There was never anything to choose, so it no longer offers a choice: **`.github/workflows/build-mobile.yml` is a constant.**

- **A leftover value is reported, not obeyed.** If `GITHUB_BUILD_WORKFLOW` is still set to anything else, both set-up panels say *"…is ignored — this platform builds mobile apps with build-mobile.yml. You can delete that variable."* Nothing breaks while it sits there; it simply does nothing.

- **The row is gone from the set-up checklist**, because a setting that is not read has no business being on a list of things to set.

## What this means for you

**Nothing to do.** You do not have to change `GITHUB_BUILD_WORKFLOW` — it is ignored either way. Deleting it just tidies up.

If you have already pushed `.github/workflows/build-mobile.yml` to your branch and opened the repository's Actions tab once, a build should now dispatch. **Check GitHub setup** will confirm all four answers before you press Build.

## A note on the one thing a rename costs

Renaming the workflow file in your repository is no longer supported — the platform asks GitHub for `build-mobile.yml` by name. That is a deliberate trade: one genuinely rare need, against a wrong value that arrives for free every time an environment file is copied from another project.
