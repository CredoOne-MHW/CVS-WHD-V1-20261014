## AS-IS

Everything from v1.0.0 to v1.11.1 is unchanged. **No screen, field, module or behaviour has been removed, renamed or moved.** This release changes three build settings and one build script. Nothing in the platform, the web app or the phone app's own code is touched.

## Update / Modifications

### Fixed: `expo-modules-core:compileReleaseKotlin FAILED`

**This was introduced by v1.10.0 and it was my mistake — the second one from the same change.** v1.11.1 fixed the signing step, the build then got five minutes further, and failed here.

Buried in about 130 harmless warnings there was exactly one error:

```
e: expo-modules-core/.../permissions/PermissionsService.kt:166:36
   Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver
   of type Array<(out) String!>?
```

**What actually happened.** v1.10.0 set the Android API level to **35**, to meet Google Play's requirement for store uploads. But that setting does two different jobs:

- **`targetSdkVersion`** is what Play requires to be recent. It is a manifest value and affects nothing at compile time.
- **`compileSdkVersion`** decides which Android API the app is *compiled against* — including every library in it.

In **API 35, Android annotated `PackageInfo.requestedPermissions` as nullable.** Expo SDK 51's own Kotlin source, written against API 34, does this:

```kotlin
return requestedPermissions.contains(permission)
```

Compiled against 35 that is an error, and it is **inside Expo's own package** — nothing in this project can patch it. Expo moved to API 35 in SDK 52; the app is on 51.

**How it was found.** The failing file was read straight out of `node_modules` here, and the Kotlin version was checked first and ruled out — it is pinned at 1.9.23 and v1.10.0 did not change it. The cause was the compile level, not the compiler.

**The fix.** The level is back to **34**, which is what every successful build up to v1.9.x used, including the working `v1.0.0.16` APK.

### This combination can no longer be set by accident

A build that asks for a level the installed Expo cannot compile against now **stops in the first few seconds**, at the branding step, with:

> *Android API level 35 was asked for, but Expo SDK 51 can only be compiled against API 34. Building anyway fails inside expo-modules-core with "Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver" — Expo's own source, which this build cannot patch. Either set `ANDROID_TARGET_SDK=34` on the platform, or upgrade the app to Expo SDK 52.*

It is **checked, not quietly clamped** — silently building something other than what was asked for is how somebody ends up wondering why Play still rejects their upload. The ceiling per Expo release is recorded in one place, so when the app moves to Expo 52 the higher level simply becomes allowed.

### Also fixed: v1.10.0 quietly dropped Android 6 phones

The same change set `minSdkVersion` to **24**, which I did not flag at the time. Expo 51's default is **23**, and that is what the shipped `v1.0.0.16` was built with — so the next build would have stopped installing on Android 6.0 devices that had the app working, with nothing saying why.

It is back to **23**. If you would rather require Android 7 and above, say so and it is one setting.

## What this means for Google Play

Stated plainly, because it is a real trade-off and not something to bury:

- **Direct-install `.apk` builds — the ones you are using — are unaffected.** They do not care about the target level.
- **New uploads to the Play Store will be refused while the app targets 34.** Play requires a recent target level for store submissions.

Raising it means **upgrading the app to Expo SDK 52 or newer**, which is its own piece of work: a major-version upgrade of Expo and React Native, every native dependency moved with it, and a full rebuild and test. It is not something to fold into a patch release, and it is not something to do quietly on the way to something else — which is exactly the mistake that produced these two failures. Say the word and I will scope it properly as its own release.

The same note applies to the 16 KB memory-page support Play also expects, which I flagged in v1.10.0 and which needs the same upgrade.

## Verified

- `npm test` — **148 checks**. The store-compliance test no longer asserts a fixed number; it reads the ceiling for the app's actual Expo version and checks the configured level is within it, so this cannot drift back.
- The guard was run both ways against the real project: asking for 35 on Expo 51 exits with code 1 and the message above; asking for 34 passes and reports `Android compile/target SDK: 34 (Expo SDK 51 supports up to 34)`.
- The whole sequence was run here against a **real `expo prebuild`**: the Gradle properties come out at 34, and all four signing values are present with `android.extraMavenRepos` intact — so the v1.11.1 fix still holds at this level.
- `npx tsc --noEmit` clean on both the platform and the app; `npm run build` clean; `npm run verify:bundle` bundles.

**Still not verifiable here:** no Android SDK in this container, so Gradle cannot be run. What is proved is that the inputs Gradle reads are now the ones that compiled successfully through v1.9.x.
