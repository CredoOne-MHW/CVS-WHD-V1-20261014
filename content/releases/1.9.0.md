## AS-IS

Everything from v1.0.0 to v1.8.16 is unchanged. **No screen, field, module or behaviour has been removed, renamed or moved.** Every existing user, role, permission, conversation, build and setting works exactly as it did before this release.

Specifically preserved:

- **Users already created stay staff.** The new user type defaults to *Staff*, so every existing row reads as it always did and nothing had to be migrated.
- **Role Management works as before.** Roles, the permission grid, the plan caps and the per-user role assignment are untouched — this release only adds to the user form.
- **Existing chats are untouched.** Every message already sent is still a text message and still renders the same way.
- **The mobile build pipeline is unchanged.** Signing, the callback, the S3 upload and the revision markers all behave as in v1.8.16.

## New Features

### Customers can be given a sign-in, and tied to the record they already are

Under **Settings → Role Management → Users** (web) and the new **Users** screen in the app, a user can now be created as one of two types:

- **Staff** — somebody who works there. This is the default and what every existing user is.
- **Customer** — somebody who signs in to talk to you, rather than to work there.

A customer can optionally be **mapped to a client or a lead** through a dropdown that searches as it is typed. It matches on name, business name, phone, WhatsApp number, e-mail address or client code, says whether each hit is a *client* or a *lead*, and shows the mapped name back on the users list afterwards.

The mapping is **optional on purpose**: a customer who is not on the books yet still gets a sign-in and can still talk. And it is one field, not two — the platform works out from the record itself whether it is a client or a lead, so the wrong one cannot be filled in.

### Roles for users created in the app

The **Users** screen is new on the phone, and a role is required on it exactly as on the web. The list shows each person's type, role and whether they are disabled; tapping a row edits them, including their role, status and password.

This screen is governed by **Role Management › Users** permission *and* by the company's **Mobile Modules** — it appears in Super Admin → Company → Mobile App as a new tick box named **Users**. For a company whose screen list was already saved, it must be ticked before it appears in the app; a company with no explicit list gets it from whatever its modules allow.

### Attachments in chats

Both the web Chats page and the app's conversation screen now take a file:

- **Images, PDF, Word, Excel, CSV and plain text**, up to **15 MB** each.
- An image appears in the conversation; anything else opens in whatever already opens that kind of file.
- The conversation list and the push notification say *"Photo: …"* or *"File: …"*, so a phone that is not open still says what arrived.

**How the files are kept.** The bytes go to the company's own S3 folder under a new `chat/` area, one folder per conversation, and never into the database. **The bucket stays private.** No message carries a usable address: a link is asked for on the tap that wants the file, it is checked against the asker's membership of that conversation *at that moment*, and it stops working after five minutes. Somebody removed from a group stops being able to open its files from that moment, with nothing having to be moved.

**Refused before it is uploaded.** A file of the wrong kind or over the limit is refused in the browser and on the phone, by name and with the actual size, rather than after a 15 MB upload completes.

## Update / Modifications

### Fixed: the numbers on the app's dashboard

All four tiles on the app's dashboard were reading a payload shape the platform has never sent. Three of them silently showed **0**, and the fourth printed `[object Object]` where a count belonged, because it rendered an object instead of a number.

They now read the real figures — new leads, follow-ups due today, converted, and total clients — and each one goes through a guard that shows `0` only when the platform genuinely sends nothing, rather than when the field is simply named something else.

### Fixed: "Add user" could never be used by the person meant to use it

A pre-existing problem, found while building the above and worth stating plainly.

The users list fetched the company's roles from `/co/roles`, which requires **Role Management › Roles** permission. Somebody granted **Role Management › Users** but not *Roles* — which is the ordinary way to let an office manager add staff without letting them rewrite permissions — got nothing back from it, so the role dropdown was empty and **"Add user" stayed disabled with no explanation**.

There is now a narrower endpoint that returns role *names only*, under the **Users** permission, exposing no permission grid. Both the web and the app use it. The web asks for it only when the wider call came back empty, so nothing changes for an administrator who has both.

### Note on what a customer can see

A customer who signs in can start a conversation with the staff the chat directory lists, and that directory shows **names and roles only** — a phone number or an e-mail address is never part of what chat sends, for staff or customers. If you would rather customers reached only specific people, say so and it can be scoped in a follow-up; it is a deliberate choice left as-is rather than changed without consent.

## Performance

- **The searchable dropdown waits 180 ms (web) / 200 ms (app) before asking**, so a six-letter name is one request and not six.
- **Every answer is cached for the session**, so backspacing to something already typed is instant and silent.
- **A late answer is discarded, not painted.** A reply that arrives after a newer query has been typed is dropped, which is what otherwise makes a type-ahead flicker between results on a slow connection.
- **Mapped names come with the users list**, resolved in one query, instead of one request per customer row.
- **Lookups are capped at 20 rows** — this feeds a box somebody is typing into, and a list longer than a screenful is no more useful than a short one.
- **Attachment bytes never pass through the database.** The upload streams to S3 and the message carries only a key.

## Logs

- Creating or changing a user is recorded as before, now including the type and the mapping.
- Every attachment creates a message row carrying who sent it, its name, size and type, and the conversation it went to.

## Build repository

`mobile/` and `.github/` must be pushed to the build repository with this release, as always. **This release adds a native dependency** (`expo-document-picker`), so a stale `mobile/` would fail to bundle. The revision markers were bumped to `1.9.0` for exactly this reason — Super Admin → Mobile App Release will report the repository as behind until it is pushed.
