## AS-IS

Everything from v1.0.0 to v1.7.1 is unchanged. Every existing build keeps working exactly as it did: with nothing new configured, pressing Build still produces the `.apk` and ad-hoc `.ipa` it always has, in the same place, on the same download page. Nothing was removed.

## New Features

- **Store build.** A build is now either:
  - **Direct install** — the `.apk` and ad-hoc `.ipa` you have always had, and still the default; or
  - **Store upload** — an **`.aab`** for Google Play and an **App Store `.ipa`** for App Store Connect, which are the only formats the two stores accept.

  Choose it with **Store build** on the company's Mobile App tab, or **What it is for** on *Mobile App Release*. Both screens say in one line what file you are about to get, before you press the button — an `.aab` handed to someone expecting to install it wastes an afternoon.
- **It uploads itself, if you let it.** With the store credentials in the build repository, a store build goes straight to Google Play's **Internal testing** track and to **TestFlight**. Without them the file is still built and kept in the company's folder, and the build row says *"kept on S3 — add … to upload automatically"*. Either way works; neither is a lesser path.
- **The result is recorded on the build**, so the builds table says *"uploaded to the Internal testing track (version code 14)"* or exactly why a store refused it — unknown application id, missing permission, a build number already used.
- **A failed upload never fails the build.** The file is already stored before the upload is attempted, so a store being unreachable costs a retry, not a rebuild.
- **Store builds are kept off the company's download page.** An `.aab` cannot install on a phone, so offering one would hand somebody a file that cannot work and no way to find out why. Super Admin still sees every build.
- **A new guide**, *Knowledge Base › Publishing to Google Play and the App Store*: the one-time set-up in each store, what to paste where, and what each refusal actually means.

## Updates / Modifications

- **Nothing can reach the public on its own.** The Play upload goes to **Internal testing** and the Apple upload to **TestFlight**. Promoting to Production, or submitting for review, stays a decision somebody makes in the Play Console or App Store Connect. This is deliberate.
- **The workflow gained one input, `target`**, which decides `assembleRelease` versus `bundleRelease` on Android and which export options are used on iOS. An older dispatch without it behaves exactly as before, because it defaults to `test`.
- **New export options file** `.github/ios-export-store.plist` (`method: app-store`). The existing `ios-export.plist` is untouched and still used for direct installs. **Note:** a store build needs an **App Store** provisioning profile in `IOS_PROFILE_BASE64`; an ad-hoc profile builds fine and is then refused on upload.
- **`MobileBuild` gained `target` and `store`** (uploaded, track, at, message). Existing rows have no value in them and are treated as direct installs, which is what they were.
- **Three new repository secrets, all optional** — add them only if you want the upload to happen by itself:

  | Secret | For |
  | --- | --- |
  | `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` | Google Play |
  | `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_KEY_P8` | App Store Connect |

  They are checked by the build itself, like the other repository secrets, and appear on the set-up panel as optional.
- **The Play upload talks to Google's own Publishing API** from `.github/scripts/play-upload.py` — no third-party action ever sees the service-account key or the bundle.
- **`latestReady()` takes a second argument**, `onlyInstallable`. The company's own page passes it; the Super Admin screens do not. Every existing caller keeps its previous behaviour.

## Before the first store build

1. **Create the app in each store** with exactly the application id / bundle id the Build screen shows, and upload one build by hand. Neither store accepts an unknown id over an API, so the first one always goes through the console.
2. **Then add the secrets above**, if you want it automatic.
3. The guide walks through both, including what each refusal means.
